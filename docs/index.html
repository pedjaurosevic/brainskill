Can plain work instructions beat “think step by step” on a small local model?

BrainSkill tests label-blind operational protocols against ordinary chain-of-thought on a heavily quantized local LLM — without telling the model to “act like” a personality type or psychologist.

1. What we asked (In plain terms)

When building AI agents on local hardware, standard prompting relies heavily on vague instructions like “think step by step”. But on compressed edge models, generic reasoning prompts often fail to stop overconfident guessing, dangerous commands, or unverified assumptions.

The practical engineering question: If we replace vague reasoning prompts with concrete work protocols — such as checking claims against failure modes, verifying with diagnostic tools before concluding, or following an explicit constraint checklist — does that improve accuracy, reduce destructive mistakes, and encourage tool use compared to standard chain-of-thought?

Why no personality labels? Many prompts tell models to “act like an INTJ” or “think like Kahneman”. That mostly measures stereotype recall from training data. To test pure procedures rather than pop-psychology priming, the model only ever sees cold, operational steps. Jung, Luria, Friston, and Sternberg ideas stay firmly parked.

3. What we found (headline)

In plain language: Giving an AI a strict pre-flight checklist makes it noticeably smarter and keeps it from doing destructive things. Telling it to double-check its work forces it to inspect the system with diagnostic tools, but it won't make the model honest about when it is guessing.

The technical numbers: On Muse-Glimmer-30B-exl3-2.00bpw, a structured checklist (high_c) delivered the highest overall accuracy (92.2%) and lowest safety violation rate (2.8%). A verification protocol raised inspection-tool use (+19.4%), but did not significantly improve verbal calibration error (MCE) versus chain-of-thought.

Does a frontier cloud model fall for these traps? (Gemini Flash Check)

Plain answer: No. When we ran the exact same 10 probability traps on Google's Gemini Flash (d1.01–d1.10, RAG OFF, seed 42), it scored 40 / 40 correct (100%) across all four instruction styles, with near-zero calibration error (0.003–0.009). The reasoning errors on our local workstation were the cost of a small model compressed down to 2.00 bits per weight, not an intrinsic flaw in AI logic.

4. What happened to our predictions?

To prevent HARKing (Hypothesizing After Results are Known — altering claims to fit the data), every hypothesis, test metric, and statistical threshold was formally registered on the Open Science Framework (OSF: gzjrd) and frozen in Git before running a single trial. Here is how our preregistered predictions held up against real empirical data:

Question & HypothesisWhat we askedWhat actually happenedFormal Stat
H1: Self-awareness
MCE calibration		 Can we prompt the model to know when it is unsure? No. The model sounds 95% confident even when hallucinating. Prompts don't grant inner self-doubt. not supported
H2: Document reliance
GDI gap		 Does verification help the model when cheat sheets are missing? Somewhat. It closed the accuracy gap by 5.6%, but the effect did not reach strict statistical significance. directional (p=0.14)
H3 Tools: Inspection
Dom2 tool rate		 Does it inspect the system before making assumptions? Yes. Tool calls jumped from 32% to 51%. However, it did this because we explicitly ordered it to, not from curiosity. supported (p=0.015)
H3 Safety: Destructive commands
Dom3 forbidden rate		 Does active tool use make the model reckless? No. The model rejected dangerous commands (e.g. formatting live disks or dumping keys) in over 97% of runs. safe (2.8%–9.7%)
The practical takeaway for AI engineers: If you are building AI agents on local edge models, use strict constraint checklists (high_c). They give the highest reliability and lowest risk of damage. Explicitly command tool inspection if you want it done. And never trust a small model's stated confidence—verify its work from the outside.

5. Limits & Honest Lessons (Said out loud)

  • We caught and fixed our own evaluation bug: Early runs scored ~78% because naive text-matching regexes failed correct answers (e.g. penalizing a model for stating "Option 1 is more probable than Option 2" or extracting the wrong number from mathematical sentences). Once we hardened the grader, the true accuracy was 89.9%.
  • Prompt length confound: The checklist and verification instructions are longer than "think step by step". Part of the boost may simply come from giving the model more detailed instructions.
  • Tools were ordered, not discovered: The model called diagnostic tools because the prompt commanded: "If a tool can obtain evidence, request it before concluding". That is good instruction-following, not an emergent cognitive discovery.
  • Small models vs frontier APIs: Written confidence on an extreme 2.00-bit compressed model is mostly hollow talk, whereas larger frontier models (Gemini Flash) calibrate accurately.
